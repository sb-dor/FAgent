# План: flutter_code_agent

## Цель

Открытое десктопное приложение на Flutter — аналог Claude Code Desktop, заточенный под Flutter-разработку.
Пользователь выбирает готового AI-агента (Claude Code, Codex, Gemini CLI и др.), открывает или создаёт
Flutter-проект и работает с ним в одном окне: чат с агентом, запуск приложения, hot reload, выбор виджета
кликом. Агент получает Flutter-знания (правила архитектуры, skills, Dart MCP-сервер) автоматически.

## Принятые решения

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Что это | Flutter Desktop-приложение, open source | Шаблон в репо уже Flutter-приложение |
| Имя | `flutter_code_agent` | `flutter_agent` на pub.dev занят (заглушка 0.0.1-alpha, 2025) |
| Агенты | Готовые агенты через Agent Client Protocol (ACP), свой цикл агента не пишем | 40+ агентов уже поддерживают ACP; подписка пользователя работает как есть |
| ACP-клиент на Dart | `acp_dart` (0.5.0, сент. 2026) — проверить перед M1, запасной вариант `dart_acp_sdk` | Не писать JSON-RPC с нуля |
| Первый агент | Claude Code через `@agentclientprotocol/claude-agent-acp` | Самый сильный в коде, у вас уже есть подписка |
| Платформы | macOS сначала; Linux/Windows — папки оставляем, код без привязки к macOS, сборка через CI позже. `web/` удаляем | Web не умеет запускать процессы; iOS-симулятор только на Mac |
| Структура | Один Flutter-проект, ядро без зависимости от UI | Workspace — когда появится реальная причина |
| Стек | control (git, закреплён на коммите), drift, freezed, l, window_manager, встроенный gen-l10n; octopus — когда понадобится навигация; архитектура по `docs/AI_INSTRUCTIONS.md` | Ваш привычный стек; репо становится эталоном правил |
| Знания для агента | Свой MCP-сервер приложения + Dart MCP-сервер, передаются в каждую ACP-сессию (`session/new` → `mcpServers`) | Один механизм для всех агентов, проект пользователя не засоряется |
| История сессий | drift (проекты, сессии, сообщения) + ACP `session/load` для продолжения, где агент это умеет | История не зависит от агента |
| Лицензия | MIT | |

## Архитектура

```
lib/
├── main.dart
└── src/
    ├── common/
    │   ├── acp/              # запуск агента как процесса, ACP-соединение, общие модели
    │   ├── flutter_daemon/   # flutter run --machine, устройства, DTD/VM service URI
    │   ├── mcp/              # MCP-сервер приложения (знания + инструменты приложения)
    │   ├── shell_env/        # PATH из login shell (GUI-приложение macOS его не наследует)
    │   ├── database/         # drift: projects, sessions, messages
    │   ├── localization/     # intl_en.arb, intl_ru.arb
    │   └── widget/
    └── feature/
        ├── initialization/       # Dependencies, DependenciesScope, шаги инициализации
        ├── workspace/            # каркас окна: сайдбар, чат, панель запуска
        ├── projects/             # список проектов и сессий (сайдбар)
        ├── project_creation/     # мастер нового проекта
        ├── chat/                 # сессия с агентом: поток сообщений, отправка промпта, отмена
        ├── permission_request/   # подтверждение действий агента (ACP request_permission)
        ├── file_diff/            # просмотр изменений, сделанных агентом
        ├── app_run/              # устройства, запуск, hot reload/restart, логи
        ├── agent_settings/       # выбор и настройка агентов
        └── widget_picker/        # выбор виджета в запущенном приложении
knowledge/                        # Markdown: правила и skills, отдаются через MCP-сервер приложения
```

Ключевая связка: приложение само держит `flutter run --machine` и передаёт адрес DTD запущенного приложения
в Dart MCP-сервер агента. Тогда инструменты агента `hot_reload`, `get_runtime_errors`, `widget_inspector`
работают с тем же запуском, который пользователь видит в панели.

### Отличия от `AI_INSTRUCTIONS.md` для этого репо

- Только десктопный UI: без `widgets/mobile/` и `screenSizeMaybeWhen`, если не понадобится узкое окно.
- Нет аутентификации и прав доступа: без `AuthenticationInProgressListener` и `*_permissions.dart`.
- Нет `ApiClient`: репозитории работают с процессами (агент, `flutter`), файлами и drift.
- Всё остальное без изменений: config-widget + InheritedWidget, `StateController` + Sequential/Droppable,
  freezed-состояния, data-контроллеры на `ChangeNotifier`, правило закрытия стримов, локализация en+ru.

### M3. Flutter-знания для агента (2 недели)

- [x] Разбить `AI_INSTRUCTIONS.md` на файлы в `knowledge/` (общие правила, по типам фич, стримы, пагинация, drift) — встроенные правила и скиллы в `assets/knowledge/`
- [x] MCP-сервер приложения: skills (`list_skills`, `load_skill`, `read_skill_file`); инструменты приложения (`app_status`, `app_logs`, `runtime_errors`, hot reload и restart, скриншот). Правила уходят в системный промпт, а не инструментом; выбранный виджет — M6
- [x] В `session/new` и `session/load` передавать этот сервер, `dart mcp-server` и свои серверы. DTD-адрес `dart mcp-server` не принимает: агент подключается своим инструментом `dtd`, адрес даёт `app_status`
- [x] Личные правила проекта: короткий AGENTS.md в репо пользователя, если он есть — подхватывается агентом сам
- [x] Правило свежести: перед добавлением пакета — `pub_dev_search` и changelog
- [x] Runtime-ошибки debug-запуска из VM service (`Flutter.Error`) — в лог запуска, «Отправить агенту» и `runtime_errors`

Готово, когда: в чистом проекте агент без подсказок делает фичу по вашей архитектуре и проверяет версию пакета.

Открытый вопрос этой вехи решён: MCP-сервер приложения работает по HTTP на `127.0.0.1` внутри
приложения (адаптер Claude отвечает `mcpCapabilities: {http: true, sse: true}`); stdio-мост — в M5,
если другому агенту не хватит HTTP.

Решения M3 (спека `docs/superpowers/specs/2026-11-01-m3-agent-knowledge-design.md`):
- Правила (встроенные и включённые свои) уходят агенту в системный промпт сессии, скиллы — через
  MCP-сервер приложения; набор фиксируется на старт сессии.
- `AGENTS.md` проекта — правило только для чтения, всегда включено и уходит агенту один раз; если
  `CLAUDE.md` уже подключает его строкой `@AGENTS.md`, приложение его не дублирует.
- У каждого чата свой токен к серверу приложения; он выдаётся заново при каждом `session/new` и
  `session/load`, токен удалённого чата отклоняется. Отдельного отзыва при закрытии чата нет: у чата
  нет состояния «закрыт».
- `hot_restart` сообщает свой результат, а не ищет ошибку в логе; `app_logs` и `runtime_errors`
  видят только текущий запуск.
- Статус Dart MCP в настройках проверяется SDK из настроек Flutter, сессии запускают его SDK
  проекта. Проверки MCP-серверов останавливаются при выходе из приложения.
- «Попробовать в чате» возвращает в текущий чат с `/имя ` в поле ввода (новый чат не открывается).
- Runtime-ошибки из VM service берутся только в debug: инспектор, который их отправляет, есть только
  там. Заголовок ошибки — её краткое описание (`A RenderFlex overflowed by 42 pixels on the right.`).
  В profile, release и без подключения разбирается текст вывода, как в M2.

## Риски

| Риск | Что делать |
| --- | --- |
| ACP или адаптер меняют протокол | Все вызовы ACP за одним интерфейсом в `common/acp/`; версии адаптеров закреплять |
| GUI-приложение macOS не видит PATH, `npx`/`flutter` не находятся | `shell_env` в M1 первым пунктом |
| App Sandbox блокирует запуск процессов | Выключить в M0; для Mac App Store не публикуемся |
| Агент не залогинен / не установлен | Понятный экран с командой установки и входа |
| Агент выполнит опасную команду | Подтверждения через ACP `request_permission`; git-коммит перед ходом агента |
| Объём (8 вех) | Критерий «готово» у каждой вехи; M4–M6 можно переставлять, M0–M3 — нет |
