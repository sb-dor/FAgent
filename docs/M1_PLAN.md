# Plan: M1 — чат с Claude Code через ACP
_Locked via grill — by Claude + Avaz. Revision 5, approved by Codex in round 5._

## Goal

В приложении можно открыть любую папку как проект, начать в ней чат с Claude Code и довести задачу до
конца, не выходя из окна: агент отвечает потоком (Markdown), видны его размышления, вызовы
инструментов и план; правки, сделанные инструментами редактирования агента, показываются как diff,
а для git-репозиториев после хода виден список всех изменённых файлов. Агент работает только в папке,
которой пользователь доверил выполнение её настроек и хуков, и спрашивает разрешения карточкой в чате
в соответствии с выбранным режимом разрешений (`default` — спрашивает обо всём опасном; немануальные
режимы — с явным согласием или заметной плашкой). Чаты сохраняются в drift и переживают перезапуск
приложения (контекст агента — через ACP `session/load`). Агент может работать в фоновом чате, пока
открыт другой. Если Claude не залогинен, вход выполняется из приложения.

Критерий готовности: открыли avera-hotel (доверили папку), попросили добавить фичу, подтвердили
правки, увидели diff и список изменённых файлов, закрыли приложение и продолжили тот же чат с
сохранённым контекстом агента.

## Approach

### 0. Зависимости
- `dart_acp_sdk: 0.1.1` (точная версия): ACP v1, клиентская сторона. Используется только внутри
  `lib/src/common/acp/`, наружу отдаются свои модели.
- `file_selector` — выбор папки; `flutter_markdown_plus` — Markdown (`flutter_markdown` discontinued);
  `crypto` (dart-lang) — хэши для `turn_files`.
- Адаптер: `npx -y @agentclientprotocol/claude-agent-acp@0.96.0`, версия — константа в коде.

### 1. `lib/src/common/shell_env/` — окружение для дочерних процессов
- `ShellEnvironment.resolve()`: один раз при старте — `$SHELL -ilc` (интерактивный login: nvm
  подключается в `.zshrc`), печатает `env -0` между уникальными маркерами. Таймаут 10 с.
- Фолбэк: `Platform.environment` + `/opt/homebrew/bin`, `/usr/local/bin`; `which(name)` по `PATH`.
- Preflight перед первым запуском агента: `node --version` (≥ 22) и `npx --version` с таймаутом 10 с;
  при провале — экран с понятной причиной и командой установки, агент не стартует.
- Шаг инициализации в `initialize_dependencies.dart` → `Dependencies.shellEnvironment`.

### 2. `lib/src/common/acp/` — процесс агента и протокол
- `AgentDefinition` — id (`claude`), имя, команда/аргументы адаптера, команды входа
  (`--cli auth login --claudeai|--console`). Команды входа берём отсюда, а не из `authMethods`
  (typed `AuthMethod` в SDK теряет поле `args`).
- **Сырой транспорт.** Нарезку на строки делает `ndJsonStream` из SDK (лимит строки
  `maximumLineBytes` = 16 МБ по умолчанию SDK; превышение закрывает соединение диагностической
  ошибкой). `RawMessageTap` оборачивает поток **уже разобранных JSON-объектов** из
  `AcpDuplexStream` — после нарезки, но до typed-декодера: каждое входящее сообщение JSON-RPC
  сначала публикуется как исходный JSON (`RawAcpMessage`), потом уходит в typed декодер SDK.
  Своего буфера у tap нет. «Сырой» здесь значит семантически исходный JSON-объект до typed-модели,
  а не побайтовая копия строки (пробелы и порядок ключей не сохраняются). Журнал пишет именно сырой JSON. Если typed-декодер не знает вариант
  `sessionUpdate`, сообщение всё равно сохранено и показывается в ленте как диагностическое.
- `AcpAgentProcess` — один процесс на агента:
  - запуск обычным `Process.start` (`ProcessStartMode.normal` — есть stdio и `exitCode`);
  - **уборка дерева — запасной путь** (`ProcessTreeKiller`, `common/acp/`): основной путь — адаптер
    сам завершает сессии и выходит по EOF stdin. Перед закрытием stdin, пока корень жив, снимается
    снимок дерева: рекурсивно `/usr/bin/pgrep -P <pid>`, для каждого PID запоминается время старта
    (`ps -o lstart= -p`). После таймаута SIGTERM/SIGKILL шлются по снимку снизу вверх, и только тем
    PID, у которых время старта совпадает (защита от переиспользования PID). Потомки, успевшие
    переподчиниться `launchd`, всё равно в снимке. Без FFI и без `detachedWithStdio` (у него нет
    `exitCode`). Тест: после остановки не осталось потомков (`npx` → node → `claude`);
  - **обязательный gate этапа 2**: тест, где фейковый агент **во время хода** запускает фоновый
    процесс, который сразу переподчиняется `launchd` (как `dev-server &`). Если после остановки он
    жив — до продолжения M1 делаем нативный helper с `setpgid`/`killpg` (агент запускается в своей
    группе процессов, остановка убивает группу), снимок `pgrep` тогда остаётся только диагностикой;
  - **stdout агента не трогается приложением**: байты идут без изменений в `ndJsonStream`;
  - stderr агента и stdout/stderr процесса входа читаются через `BoundedLineSplitter`: строка
    обрезается на 2000 символов прямо при чтении (хвост отбрасывается, не накапливается), ANSI-коды
    вырезаются, в памяти кольцо на 500 строк.
    `CLAUDE_AGENT_LOGS` по умолчанию **не** задаётся (только переключателем отладки);
  - дедлайны: spawn + `initialize` 120 с (первый `npx` качает пакет), `session/new`/`load` 60 с;
    при истечении — процесс убивается, пользователю показывается хвост stderr;
  - `initialize`: `protocolVersion: 1`, `fs` и `terminal` выключены,
    `_meta: {"terminal-auth": true}` (иначе адаптер не отдаёт `authMethods`); сохраняем
    `agentCapabilities`;
  - **single-flight**: старт и остановка идут через один `Future`; у каждого запуска есть номер
    поколения, и сессии/запросы старого поколения после рестарта отбрасываются;
  - остановка (вызывается всегда при выходе из приложения, даже если ходов нет): `session/cancel`
    для активных ходов → ждём ответы `prompt` до 3 с → снимок дерева → закрыть stdin → **ждём
    `exitCode` до 5 с (штатный выход по EOF)** → только если не вышел: SIGTERM дереву → через 5 с
    SIGKILL дереву. Процесс входа убивается так же;
  - падение процесса: несохранённые события сбрасываются в журнал, сессии получают системное
    событие и статус `error`; следующий промпт стартует новое поколение (без автоцикла рестартов).
- **Вход в аккаунт — на уровне агента, не сессии.** `AgentAuth` (single-flight на `agentId`): один
  процесс входа на агента; пока он идёт, все сессии агента в `needsAuth` показывают «Выполняется
  вход». После успеха каждая такая сессия повторяет **прерванную операцию настройки** (`load`/`new`),
  если ошибка случилась на ней; если на промпте — показывает кнопку «Повторить последний промпт».
- `AcpClientHandler` — запросы агент → клиент:
  - `session/request_permission` → `PermissionBroker`, ключ — **JSON-RPC id запроса**; ответ
    отправляется ровно один раз (выбор пользователя или `cancelled` при отмене хода/остановке),
    повторные и поздние ответы игнорируются;
  - `fs/*`, `terminal/*` — не заявлены, ответ `method not found`.
- `AgentHub` — реестр процессов и живых сессий (`LiveSession`):
  - **две полосы операций на сессию.** Полоса настройки (mutex): `load`, `new`, `setConfig`,
    отправка `session/prompt`. Mutex держится только на время отправки запроса, **не** на время
    ожидания конца хода; повторный промпт во время хода запрещён машиной состояний, а не mutex'ом.
    Управляющая полоса без очереди: `cancel` и ответы на разрешения исполняются сразу;
  - явная машина состояний сессии. Переход вне таблицы проверяется **в рантайме** (и в release):
    операция отклоняется с `StateError`, сессия получает системное событие с диагностикой;
    `assert` — только дополнительная проверка в debug:

    | Из | Событие | В |
    |---|---|---|
    | `cold` | промпт | `starting` |
    | `starting` | процесс готов | `loading` (есть `acpSessionId`) / `creating` |
    | `loading`/`creating` | успех | `idle` (только здесь сессия становится живой) |
    | `loading`/`creating` | ошибка | `setupFailed` (запоминаем, какая операция) |
    | `setupFailed` | «Повторить» | `starting`/`loading`/`creating` (та же операция) |
    | `setupFailed` (после load) | «Начать заново», подтверждено | `creating` |
    | `idle` | промпт | `running` |
    | `running` | запрос разрешения | `awaitingPermission` → `running` после ответа |
    | `running`/`awaitingPermission` | Стоп | `cancelling` → `idle` по ответу prompt |
    | `cancelling` | нет ответа 15 с | `cancelling` + кнопка «Принудительно остановить агента» |
    | `cancelling` | принудительная остановка, подтверждена | процесс агента убит → его сессии в `error` |
    | `starting`/`loading`/`creating`/`running` | `authRequired` | `needsAuth` (+ прерванная операция) |
    | `needsAuth` | вход успешен | повтор прерванной настройки или `idle` с кнопкой «Повторить промпт» |
    | любое | падение процесса / ошибка | `error` |
    | `error` | промпт или «Повторить» | `starting` (новое поколение процесса) |
    | любое | закрытие приложения | `disposed` |

  - `session/load`: на время load сырые события этой сессии не пишутся в журнал (повтор истории).
    Ошибка load → `setupFailed` с двумя действиями: «Повторить» (тот же `acpSessionId`) и
    «Начать новую сессию агента» — разрушительное, с подтверждением «контекст будет потерян»;
    новый `acpSessionId` и системное событие записываются в одной транзакции.

### 3. Репозитории (граница между фичами и `AgentHub`/drift)
- `IProjectsRepository` (drift + файловая система), `ISessionsRepository` (drift),
  `IAgentSessionRepository` (обёртка `AgentHub`: статус, prompt, cancel, config, auth, поток событий
  сессии), `IProjectFilesRepository` (список файлов для `@`).
- `SessionEventStore` — ровно один на `sessionId`: им владеет app-scoped `IAgentSessionRepository`
  (map по `sessionId`), UI только подписывается. Создаётся при первом обращении, читает журнал из
  drift один раз, дальше дописывает события в память и в drift (единственный писатель сессии).
  Живёт, пока сессия живая или есть подписчики; закрывается при остановке сессии без подписчиков и
  в `AgentHub.dispose()`. Drift watch для ленты не используется — дубликатов нет.
- Порядок записи — **одна упорядоченная очередь записи на сессию**, `seq` выдаётся в порядке
  постановки в очередь, запись в drift идёт строго по возрастанию `seq`:
  - обычные frames агента публикуются в UI сразу и копятся в очереди; очередь сбрасывается одной
    транзакцией раз в 200 мс, а также при конце хода/отмене/ошибке/падении/`dispose`;
  - **durable-события** (`prompt`, `permission_request`, `permission_resolution`, `system`,
    `turn_files`) сначала сбрасывают всё, что накопилось перед ними, и коммитятся в той же
    транзакции; только потом запрос уходит агенту или событие становится видимым/активным в UI.
    Кнопки карточки разрешения активируются после записи `permission_request`. Если запись не
    удалась: для исходящих запросов (`prompt`) — запрос не отправляется; для входящего
    `permission_request` — агенту ровно один раз уходит ответ `cancelled`, запись брокера
    удаляется, ход переводится в контролируемую ошибку. Ошибку записи сообщает отдельный
    **временный канал ошибок UI** (не журнал: drift в этот момент недоступен);
  - при аварийном падении самого приложения можно потерять ≤ 200 мс обычного вывода агента, но
    никогда — событие, которое следует за ним причинно.

### 4. База данных (drift, schemaVersion 1 → 2, step-by-step migration)
- `beforeOpen`: `PRAGMA foreign_keys = ON`. Снимки схем `drift_schemas/` + `SchemaVerifier` тест.
- `projects`: + `isFlutter` (bool, default `false`, backfill при первом открытии проекта),
  + `trustedAt` (nullable).
- `sessions`: `id`, `projectId` (FK, cascade), `agentId`, `acpSessionId` (nullable), `title`
  (первые 60 символов первого промпта), `createdAt`, `updatedAt`.
- `session_events`: `id` (autoinc), `sessionId` (FK, cascade), `seq`, `origin` (`user|agent|app`),
  `kind`, `payload` (сырой JSON), `createdAt`; **`UNIQUE(sessionId, seq)`**. `seq` выдаёт
  `SessionEventStore` (единственный писатель сессии) синхронно в момент постановки события в
  очередь (следующий после последнего `seq` из drift при открытии store); транзакции только
  вставляют строки строго по возрастанию `seq` и служат барьерами для durable-событий.
- Виды `kind`: все `sessionUpdate` ACP, `prompt`, `permission_request` (JSON-RPC id, toolCallId,
  варианты), `permission_resolution` (id, выбранный вариант или `cancelled`/`stale`), `system`,
  `turn_files` (список изменённых файлов). Незавершённые `permission_request` при загрузке
  истории помечаются `stale`.
- **Каждый сырой frame — отдельная неизменяемая строка.** В базе ничего не склеивается; чанки
  объединяются только в `ChatTranscript.fold` по `(messageId, kind)`. Объём (тысячи строк на ход)
  для SQLite приемлем; проверить на длинном ходе в ручной проверке.

### 5. Доверие к папке (до первой ACP-сессии в проекте)
- Адаптер исполняет `.claude/settings.json` и хуки из папки проекта. Перед первым промптом в
  проекте без `trustedAt` — диалог «Доверяете этой папке? Агент выполнит её настройки и хуки»
  (с перечнем найденных `.claude/settings*.json`). Без согласия сессия не создаётся.
- Режим разрешений: после `session/new`/`load` читаем текущий режим. Если он `bypassPermissions` —
  поле ввода заблокировано до явного подтверждения (сохраняется на сессию). `acceptEdits`/`auto`
  показываются заметной плашкой у поля ввода (это выбор пользователя в его настройках Claude).

### 6. Сворачивание событий в ленту — чистая функция
- `ChatTranscript.fold(List<SessionEvent>) → List<ChatItem>`: `UserMessage`, `AgentMessage`,
  `AgentThought`, `ToolCallItem` (id, title, kind, status, текст / diff / ссылки), `PlanItem`,
  `PermissionItem` (ожидает / решён / устарел), `TurnFilesItem`, `SystemItem`, `UnknownItem`
  (диагностика для неизвестных событий).
- `tool_call_update` обновляет `ToolCallItem` по id; сообщения различаются по `messageId`.

### 7. Фичи (одна ответственность на фичу)
- `projects` — список проектов (Sequential, watch).
- `project_opening` — выбор папки, проверка Flutter, upsert (Droppable).
- `project_trust` — диалог доверия (Droppable).
- `sessions` — чаты проекта со статусом из `IAgentSessionRepository` (Sequential, watch);
  «Новый чат» создаёт строку, ACP-сессия — при первом промпте.
- `chat` — лента из `SessionEventStore` (Sequential).
- `prompt_sending` — отправка (Droppable); «Стоп» вызывает `cancel` напрямую (вне `handle`).
  Enter — отправить, Shift+Enter — перенос; во время хода отправка заблокирована.
- `turn_files` — для git-репозиториев, до и после хода:
  `git status --porcelain=v1 -z --untracked-files=all` (пути из NUL-разделённого вывода, без
  разбора по строкам) **плюс** отпечаток всех путей, грязных до хода (` M`, `??`,
  переименования — по новому пути), считается в Dart в isolate по `lstat`
  (`FileSystemEntity.typeSync(followLinks: false)`), без перехода по ссылкам:
  обычный файл — SHA-256 содержимого (`package:crypto`); symlink — текст цели (`Link.targetSync`);
  каталог / FIFO / устройство / удалённый путь — типизированная метка без открытия файла.
  **Снимок «до» обязательно завершается до отправки `session/prompt`** — ход ждёт его (UI не
  блокируется, поле ввода показывает «Готовлю ход…»). Изменённым считается путь, который
  появился/исчез в статусе **или** у которого сменился хэш. Результат — durable-событие `turn_files`
  (видны и правки Bash, хуков, форматтеров). Тесты: файл грязный до хода и изменённый ходом,
  untracked, переименование, удаление, бинарный файл, имя с переводом строки, symlink наружу
  проекта (цель не читается), изменённая цель symlink, FIFO (подготовка хода не зависает).
- `file_mention` — `@` с автодополнением: `git ls-files -z` или обход папки (`followLinks: false`,
  без `build/`, `.dart_tool/`, `.git/`, лимит 5000); путь проверяется через `resolveSymbolicLinks`,
  что он внутри проекта; уходит как `resource_link` с `Uri.file(path).toString()`.
- `permission_request` — карточка с вариантами из запроса (Droppable на ответ).
- `session_config` — `configOptions` как union `select` → выпадающий список, `boolean` →
  переключатель, неизвестный тип → только чтение. Состояние обновляется только из ответа агента.
- `agent_auth` — UI над `AgentAuth`: при `needsAuth` карточка «Войти через Claude.ai / Console»;
  вывод процесса входа (через `BoundedLineSplitter`) показывается в карточке; дальнейшее поведение —
  по машине состояний (повтор настройки или кнопка «Повторить последний промпт»).
- `app_close` — `setPreventClose(true)`; если есть сессии в любом нетерминальном состоянии
  (`starting`, `loading`, `creating`, `running`, `awaitingPermission`, `cancelling`) или идёт вход
  (`AgentAuth.isRunning`) — диалог «Агент ещё работает в N чатах». `AgentHub.dispose()` выполняется
  только после подтверждения (или сразу, если работающих нет), затем окно закрывается.

### 8. Тесты
- Фикстуры: записанные NDJSON-сессии реального адаптера 0.96.0 → `test/fixtures/acp/`.
- `ChatTranscript.fold` — юнит-тесты на фикстурах, включая неизвестный `sessionUpdate`.
- `AgentHub` против фейкового агента (агентская сторона `dart_acp_sdk`, in-memory): гонки
  start/load/cancel, **Стоп во время долгого хода**, несколько разрешений в одном ходе, повтор при
  load, single-flight рестарта, вход с двумя сессиями в `needsAuth`, все переходы таблицы состояний,
  запись `prompt` до отправки (и отказ drift → запрос не уходит).
- Реальный дочерний процесс: маленький Dart-скрипт фейкового агента, который сам порождает
  потомка, — уборка всего дерева без сирот, зависший child, строка stderr длиной 10 МБ без перевода
  строки, битый NDJSON, flush при падении.
- Контрактный тест адаптера 0.96.0 (`@Tags(['adapter'])`, нужны сеть и логин, не в CI):
  `initialize` с `terminal-auth`, режимы, `session/load`, формат diff.

## Key decisions & tradeoffs
- **Готовый агент через ACP**, свой цикл агента не пишем; цена — зависимость от адаптера.
- **`dart_acp_sdk` 0.1.1** за собственной границей `common/acp/` плюс сырой транспорт: typed-модели
  для логики, сырой JSON для журнала.
- **`npx` с закреплённой версией** (выбор пользователя). Целостность — та же модель доверия, что
  у установки Claude Code через npm (registry integrity); собственный артефакт с хэшем — к M7.
- **Один процесс адаптера на агента** + single-flight, поколения и очередь на сессию.
- **Журнал сырых событий** (frame = строка, склейка только при отображении) + `SessionEventStore`
  как единственный путь к UI; действия пользователя пишутся до отправки, вывод агента — пачками.
- **Две полосы операций на сессию**: mutex только на отправку запросов, отмена и разрешения — вне
  очереди. Вход в аккаунт — single-flight на агента.
- **Уборка дерева процессов по снимку `pgrep -P` с проверкой времени старта** вместо нативного
  helper'а с группами процессов: сохраняет `exitCode` и stdio, без FFI и сборки нативного кода;
  основной путь остановки — штатный выход адаптера по EOF. Решение проверяется обязательным
  тестом с фоновым процессом, переподчинённым `launchd`; провал теста переключает M1 на helper.
- **История — наша, контекст — агента.** Повтор `session/load` не пишем; потеря контекста —
  только по явной кнопке.
- **Diff только для правок через инструменты агента**; полный список изменённых файлов — через
  `git status` до/после хода (только git-репозитории). Отката хода в M1 нет.
- **Доверие к папке** перед первой сессией; `bypassPermissions` — только с подтверждением.
- **Повтор промпта после входа — только по кнопке**, никогда автоматически.

## Risks / open questions
- Уборка дерева через снимок `pgrep -P` не видит процессы, переподчинённые `launchd` до снимка
  (фоновые процессы, запущенные агентом). Это решается не в «рисках», а обязательным тестом-gate
  этапа 2: если он падает — нативный helper с `setpgid`/`killpg` входит в M1.
- Какой код ошибки адаптер возвращает на `session/load` несуществующей сессии — выяснит контрактный
  тест; до этого любая ошибка load ведёт в `setupFailed` с выбором пользователя.
- `turn_files` не различает изменения агента и пользователя, сделанные во время хода; хэширование
  грязных путей перед ходом на большом грязном репозитории может задержать старт хода на секунды.
- Первый `npx` без сети / битый npm-кэш — экран ошибки с хвостом stderr.
- Нативный `claude` из optional dependency может не поставиться — тогда ошибка старта
  (запасной `CLAUDE_CODE_EXECUTABLE` — после M1).
- `$SHELL -ilc` с интерактивными плагинами может зависнуть до таймаута — фолбэк есть, но окружение
  может быть неполным.

## Out of scope
- Клиентские `fs/*` и `terminal/*`, картинки в промпте, git-снимки и откат хода.
- Другие агенты (M5); MCP-серверы в сессии (M3: stdio-сервер с `"type": "stdio"` адаптер выбрасывает).
- Панель запуска (M2); переименование, удаление, форк, поиск и экспорт чатов.
- Редактирование секретов в выводе входа (вывод только локально на экране пользователя).
- Linux/Windows-проверки.
